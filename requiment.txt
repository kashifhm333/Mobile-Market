# MASTER PROMPT: Build MobileMart — Production-Grade Full-Stack Marketplace

## 1. Your Role

Act as a senior software architect, full-stack developer, UI/UX engineer, database architect, application security engineer, DevOps engineer, and QA engineer.

Your task is to transform my existing UI design into a **complete, secure, maintainable, tested, production-ready web application** named MobileMart.

Do not build a simple demo, static prototype, or collection of disconnected pages. Build a real application with a functional frontend, backend, database, authentication, authorization, business logic, validation, error handling, tests, and deployment documentation.

Work systematically. Understand the requirements and architecture before writing the main application code.

## 2. Project Overview

**Project name:** MobileMart

**Purpose:** An online marketplace for buying and selling new and used mobile phones.

MobileMart connects people who want to sell their phones with people who want to buy them.

There are three primary types of visitors:

1. Guests who can browse and search phone listings.
2. Registered users who can buy, sell, manage listings, save favorites, and contact other users.
3. Administrators who manage users, listings, reports, and marketplace moderation.

A registered user can be both a buyer and a seller. Do not create separate buyer and seller account types.

### Core business rule: No online payment processing

Buyers and sellers negotiate and complete their payments directly outside MobileMart.

MobileMart must not collect money, process payments, hold funds, offer escrow, store payment credentials, or claim that a payment has been verified.

The application manages listings, buyer inquiries, seller communication, and listing status. The seller confirms when a phone has been sold.

## 7. Database Design and Business Entities

Design the MongoDB schema before implementing the API.

### User

Include identity, authentication, public profile, role, account status, timestamps, and any required verification fields.

Never return password hashes or private authentication fields through public API responses.

### Listing

Support new and used phones.

Recommended condition values:

- `NEW`
- `LIKE_NEW`
- `GOOD`
- `FAIR`

Recommended listing statuses:

- `DRAFT`
- `ACTIVE`
- `RESERVED`
- `SOLD`
- `ARCHIVED`
- `REJECTED`

Define valid status transitions. A listing must not become sold simply because a buyer submits an inquiry.

Validate price, currency, image count, field lengths, brand, model, condition, location, and other relevant inputs.

Store image metadata and storage URLs rather than image binaries in ordinary MongoDB listing documents.

### Favorite

Create a unique compound index on `(userId, listingId)` to prevent duplicate favorites.

### Conversation and Message

Ensure only the buyer, seller, or an authorized administrator can access relevant conversation data.

Prevent arbitrary users from reading messages by guessing a conversation ID.

### Inquiry or Deal

Distinguish inquiry, negotiation, reservation, and seller-confirmed sale states.

Do not create a payment entity or payment-processing service.

### Report and AuditLog

Support listing and user reports, moderation status, reviewer information, and important administrative audit events.

Use appropriate indexes for common searches, lookups, sorting, pagination, and authorization-related queries.

Implement pagination limits and protect against expensive unbounded queries.

## 8. Backend API and Business Logic

Use a versioned REST API under `/api/v1`.

Implement consistent request validation, response formats, HTTP status codes, and error messages.

### Authentication

Provide endpoints for:

- Registration.
- Login.
- Logout.
- Current user profile.
- Refresh or session renewal, if using refresh-based authentication.
- Email verification.
- Password reset.
- Profile updates.

Choose a secure authentication strategy and document it.

Prefer secure, HTTP-only, appropriately configured cookies for browser sessions or tokens. If using cookies, implement CSRF protection where required. Configure CORS for explicit trusted frontend origins.

Never store long-lived authentication tokens in browser local storage by default.

Use a maintained password-hashing library with suitable parameters. Implement login rate limiting, secure password-reset tokens, token expiry, and generic responses where needed to prevent account enumeration.

- Listing search and pagination.
- Listing details.
- Creating a listing.
- Updating a listing.
- Publishing a draft.
- Archiving a listing.

### Favorites

Implement add, remove, and list-favorites endpoints.

Enforce unique favorites and user ownership.

### Conversations and Inquiries

- Starting an inquiry.
- Listing the user's conversations.
- Viewing a conversation.
- Sending messages.
- Marking messages as read.
- Closing an inquiry.

### Reports and Administration

- Reporting listings and users.

- Authentication requirements.
